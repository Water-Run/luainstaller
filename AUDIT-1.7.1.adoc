== V71-01：混合换行误删 Lua 代码

优先级：P1，程序语义错误。

`analyzer.prepareSource`、独立运行时、内嵌运行时和运行时发现的快照处理，
都先搜索整份源码中的 CRLF，再退回搜索单个换行。如果 shebang 以 LF 结束，
而下一条语句以 CRLF 结束，剥离范围就跨过第一条语句。

[source,lua]
----
#!/usr/bin/env lua
local value = 41
return value + 1
----

复现文件的第一行使用 LF，第二行使用 CRLF。基线将第二行一起删去，
运行时报告 `value` 为 nil。若被删的语句是检查或 `require`，也会改变分析结果与执行含义。
官方 Lua 和 LuaJIT 均复现。

修复从第一个 CR 或 LF 定位行尾，只合并紧邻的双字节换行，保留后面的全部源码，
并用一个换行占位保持行号。四处实现同步修改。

回归覆盖 BOM、有/无 shebang、LF/CRLF/CR/LFCR、错误行号、首条依赖、三种发现模式、
独立与内嵌运行时，以及移除原始源码后运行的目录、解包和免解包产物。
通过原生解释器文件加载器的集成用例使用各 ABI 都接受的 LF shebang。

== V71-02：显式 Lua 输入绕过依赖限制

优先级：P2，已声明配额未统一执行。

在入口不含依赖时，通过 `include` 提供两个 Lua 文件并设置 `max_deps = 1`，
基线的 static、manual 和 runtime 三种模式都会返回成功。发现阶段计数完成后，
`applyManualInputs` 继续添加文件却没有检查总数。LuaJIT 下，一个 Lua 输入与一个
FFI 文件也能分别通过局部限制，形成超过单一预算的最终计划。

修复在合并依赖时统一计数，在读取新增手动文件前拒绝超限；同一路径去重，
入口本身不额外计数，排除项不会占用手动输入名额。FFI 名称数量继续单独受相同上限约束。

回归覆盖四个公共操作、三种发现模式和两种 CLI，核对错误类型、`current_count`、
`limit` 与输出未创建；也覆盖重复项、排除项、恰好达到限制及 Lua/原生/FFI 混合输入。

== V71-03：不可表示的依赖预算进入运行时生成

优先级：P2，输入校验与发现模式不一致。

`max_deps = 1e100` 是有限数值，旧校验还把它视为整数；static 与 manual 会接受，
runtime 却在生成 trace 脚本时因 `%d` 无法表示该值而返回内部 `LuaInstallerError`。
该输入在官方 Lua 下有独立复现。

现在统一接受不超过 2147483583 的正整数，为 trace 额外的 64 条记录留出空间，
保证生成的计数在 Lua 5.1 使用的 32 位有符号格式化范围内。
超限请求在发现前返回带 `option = "max_deps"` 的 `InvalidOptionsError`。
回归覆盖最大可移植值、紧邻超限值、极大有限数值、四个操作、三种发现模式和两种 CLI。

== V71-04：独立安装遗漏 notices 引用的许可证

优先级：P2，交付材料缺失。

1.7.0 源码包包含 `LICENSES/LuaJIT-MIT.txt`，`THIRD_PARTY_NOTICES.md` 也引用它；
但 `tools/install.lua` 的固定复制清单没有加入该文件。官方 Lua 和 LuaJIT 两种
独立安装树均复现缺失，而嵌入式分发材料中的文本已存在。

修复补齐安装清单。安装回归逐份比较主许可证、GPL、Lua、LuaJIT 和 notices，
避免只检查主许可证导致新增材料漏装。

== V71-05：同时间戳的最新日志查询返回旧记录

优先级：P2，诊断顺序错误。

日志时间戳精度为秒，同一秒内写入两条记录后，默认倒序加 `limit = 1`
可能返回第一条。排序比较器只看时间戳；Lua 的表排序不保证相等元素的顺序。
独立私有日志目录中固定时间戳后，已复现最新记录丢出查询结果。

现在以时间戳为主键，时间相同时按原始写入位置排序，再应用数量限制。
正序和倒序分别保留对应的写入顺序；筛选不改变相对顺序。
回归覆盖同秒写入、不同时间戳、level/source 筛选、limit 与两套日志命令。

== V71-06：Windows 已退出进程的身份被误当作存活证据

优先级：P1，崩溃后的输出与锁恢复被阻止。

官方矩阵的 Windows Lua 5.5 在 `after-backup` 恢复阶段出现“活动或不可恢复事务”。
随后审查发现，`lock_owner.isAlive(pid, identity)` 只要还能读取匹配的进程启动身份，
就直接返回存活。Windows 进程退出后，其对象可因其他进程持有句柄而继续存在，
这时启动信息仍然可读；参见
link:https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process[Microsoft 进程终止说明]。

在原生 Windows/MSVC 的受控复现中，C 测试驱动等待子进程退出，但保留其句柄，
再启动 Lua 观察进程。修复前得到 `identity_readable=true`、`pid_alive=false`、
`identity_alive=true`，独立确认了判活错误。
原矩阵没有保留当时的进程快照，因此不把其通用错误日志当作这一原因的唯一证明。

修复在身份匹配后查询真实进程状态；无法查询时仍返回未知，不据此回收锁。
回归覆盖保留对象的已退出进程、正常存活、身份不匹配和状态查询失败，并由原生
Windows 事务恢复测试核对备份恢复、发布和清理边界。

== C71-01：统一原生依赖计数

基线指南把 `max_deps` 描述为 Lua 模块数量，因此不将未统计 C 模块单独宣称为
违反旧文档的漏洞。此次将选中的 Lua、原生和 FFI 文件统一计数，避免同名选项
在不同输入路径上产生不同的总量边界；静态发现也在新增原生模块时检查预算。

这是配额语义的收紧。原来原生依赖较多的项目可能需要提高 `--max-deps`。
双语使用指南、变更记录、文档契约和混合输入回归已同步。

== 已排除与保留的边界

* 手动 `--include` 接受 Lua 源文件，不接受 C 库。把它与 FFI 同时使用的最初线索，
  不构成已支持行为的回归；同一原生文件同时由静态 `require` 和 FFI 选择有专门计数回归。
* LuaJIT 的版本、GC64、Lua 5.2 兼容设置、可用内置能力仍在库探测和目标启动时核对；
  JIT 开关属于应用行为，不当作运行时身份变化。
* 运行时发现执行用户代码，构建工具链和工作区仍需可信；资源配额不等于代码沙箱。
* 现有目录切换的可见间隙、断电持久性、系统原生依赖、Windows 代码页和旧物理主机边界保留。
* 本轮平台声明以 Linux 与 Windows/MSVC 原生门禁为准，补充物理主机未通过时不扩大承诺。
