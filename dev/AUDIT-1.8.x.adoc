== 补充平台迭代

* Termux 的完整 5.4 验收在单文件发布时复现硬链接被拒绝。使用原生不可覆盖重命名，
  不可用时保留原子硬链接方式；没有使用先检查再覆盖的普通重命名。
  新套件同时检查正常发布、既有目标、符号链接和发布期间出现的目标文件。
  实际 Termux 的发布与独立安装两项回归通过。
* macOS 的大小写不敏感目录使 MoonScript 输入别名被当作外部输入，材料位置不一致；
  旧测试还假定所有 POSIX 文件系统区分大小写。按私有工作目录的实际行为处理别名，
  用文件身份区分同一来源和内容相同的不同文件，拒绝已有编译目标；macOS 原生回归通过。
* 新的 POSIX 动画使用 O_NOFOLLOW，macOS SDK 在严格 POSIX 声明下隐藏该常量。
  显式启用 Darwin 声明后，原生编译、发布与 MoonScript 回归通过。
* FreeBSD 头文件会把 POSIX 特性宏规范化，生成文件再次定义该宏时严格编译失败。
  模板、内嵌模板和生成前导声明统一检查已有宏；编译回归带入等价的外部定义。
* Termux 的真实应用上下文允许搜索系统父目录，却拒绝以只读方式打开它们。
  Android 解包器用 O_PATH 逐层定位父目录，继续检查目录类型、身份和归属，
  私有缓存仍按原方式打开和校验。原生 headerless_build 的解包回归已通过。
* 严格 Linux 编译器的 Android 宏夹具没有 Bionic 的 O_PATH 声明；按声明可用性选择
  父目录访问方式，保留 Android 原生修复；同一 C99/消毒器回归修复前失败、修复后通过。
* 现代 Windows 的实际移动目录回归遇到短暂的错误 5，诊断在等待 100 毫秒后成功。
  用原生读句柄固定目录复现失败；移动操作在一秒内重试暂时占用，期间核对源身份，
  目标出现后停止重试，保留不可覆盖的原子移动。
* 五 ABI 并行构建暴露 LuaRocks 临时目录冲突；两个官方测试入口分别隔离每个 ABI 的
  临时目录。FreeBSD 的超时回归同时检查进程状态，区分正在运行和已终止待回收的后代。
* 旧 Windows 的 MinGW.org SDK 缺少所需 API 声明，原始失败按环境阻塞保留。
  改用任务私有的完整 MinGW-w64 SDK 后，原生版本与工具链预检通过；完整复测单独记录。
* Windows 的仅属性句柄不参与共享检查，旧的祖先目录保护实际仍允许移动。
  直接执行产品 C 原语的原生夹具已复现；目录句柄增加遍历权限以实际阻止名称替换，
  枚举期间也固定根目录和当前目录，解包器使用相同的有效访问方式。
  保留子项操作所需的写共享；只读共享会阻止正常的子目录移动，这项原生失败也已保留。
* 每 ABI 隔离的临时目录在 Windows 五 ABI 门禁中暴露深路径解包失败。
  解包文件操作和子进程启动使用宽字符长路径接口，目录遍历从根部保留扩展路径，
  同时补充实际生成的解包器目录保护原语回归。
* macOS 的材料导出路径可能含系统临时目录别名；先拒绝目标本身的符号链接，再解析
  真实路径并执行既有祖先校验。Android 的 ELF 冲突夹具使用真实宿主 OS；FreeBSD
  的运行时不提供 LeakSanitizer，保留地址与未定义行为检查并单独说明此项不适用。
* 64 位旧 Windows 的 32 位注册表视图没有 MachineGuid，使 32 位 Lua 缺少进程身份；
  原生只读检查已确认两个视图的查询结果，身份查询统一选择本机视图。
* 补充测试的归档目录曾继承 SSH 的组可写 umask，导致相对输出被正确拒绝；只修正
  任务自有副本权限后复测。私有 Lua 5.1/5.2 SDK 的严格 ANSI 标志关闭了厂商 Windows
  能力，按原生 GNU 配置重建；这些环境失败不记为产品通过。

Windows 原生 MSVC 的目录保护、生成解包器编译和单文件执行三项回归已通过，
包含长路径下的提取、模块加载、缓存修复和递归清理。macOS 的五个官方 Lua

== Windows 进程身份清理

旧 Windows 的额外恢复检查出现子进程异常结束后，复核发现进程树清理只比较父 PID，
并在递归结束后才打开目标进程。Windows 会复用 PID，过期父子关系可以指向无关的旧
进程，甚至形成回环。独立原生夹具用真实进程创建时间和受控进程枚举复现：修复前
会结束早于当前父进程创建的进程；修复后保留该进程和根进程，结束实际子进程。

清理现在保留进程句柄，检查创建时间，重新验证存活的父子关系，并拒绝祖先回环。
看门狗也通过已保留的子进程句柄查询身份。使用的接口仍兼容 XP。
参考 https://github.com/microsoft/dcp/issues/274[Microsoft 的同类 PID 复用问题]
和 https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes[GetProcessTimes 文档]。

旧系统两次未重现的超时另行保留；Lua 5.2 的发布后恢复阶段在未修改产品代码的
隔离追踪中已通过，不能把它直接归因于新发现的身份缺陷。其余恢复边界继续按原预算复测。

同一原生回归修复前失败、修复后通过。完整 Windows 原生套件、进程边界与工作目录
检查已分别在现代 MSVC 和旧系统的 GCC/32 位 Lua 5.2 下通过；五 ABI 的 x86/x64
宿主 DLL 严格编译及 XP 导入检查通过。完整事务恢复复测保持原有驱动预算继续执行。

清理函数改用已保留句柄后，旧的静态调用形式契约需要同步；原生行为夹具已通过，
完整边界套件按新的身份保留调用形式重新验证，131 项通过。
