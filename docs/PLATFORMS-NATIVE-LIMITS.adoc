[#platforms-contract]
== Build where you'll run

`luainstaller` makes native executables and doesn't cross-compile. The
executable fits the machine that built it: same operating system, same CPU
architecture, same Lua version.

To ship for Linux, Windows and macOS, build three times, once on each.

`--target-os` doesn't change this. It only makes the build fail when it's
run on the wrong kind of machine, which is handy in scripts.

[#platforms-lua]
== Lua versions

Official Lua 5.1, 5.2, 5.3, 5.4 and 5.5 work. LuaJIT doesn't.

The interpreter running `luainstaller` decides the version. The headers,
the Lua library and every C module you bundle must be that same version.
Before finishing a build, the new executable is started once to confirm
the versions line up.

[#platforms-toolchains]
== What each system needs

[cols="1,2,2",options="header"]
|===
|System |Compiler |Lua runtime in the bundle

|Linux, FreeBSD, other Unix
|`cc`, `gcc` or `clang`
|shared `liblua` copied into the bundle, or static `liblua.a`

|macOS
|Xcode Command Line Tools
|static `liblua.a` preferred; a dylib also works

|Windows
|MSVC or MinGW-w64
|`lua5x.dll` next to the executable

|Android (Termux)
|`clang` from Termux
|shared or static, as on Linux
|===

If headers or the library aren't found automatically, pass
`--lua-prefix /path/to/lua` (or set `LUAI_LUA_PREFIX`). An explicit prefix
is used as given; `luainstaller` won't quietly fall back to another Lua it
finds.

[#platforms-windows]
== Windows, including XP

MSVC builds link the C runtime statically, so the result doesn't need the
Visual C++ Redistributable.

x86 and x86_64 executables are built against the Windows XP API by
default. That only helps if the rest of the toolchain supports XP too:

[%interactive]
* [ ] a compiler and C runtime that target XP (an XP-capable MSVC toolset,
      or a MinGW runtime that runs on XP)
* [ ] a `lua5x.dll` built with that same toolchain
* [ ] PowerShell 2 or later on the build machine

WARNING: A current Visual Studio or UCRT build compiles without complaint
and still won't start on XP.

To build *on* XP, start from the compiler's own command prompt, set
`LUAI_CC` if the compiler isn't detected, and usually pass `--lua-prefix`.

Other notes:

* ARM and ARM64 target Windows 8 and later, since Windows on ARM didn't
  exist before that.
* File paths use the system code page. On XP, plain ASCII paths are the
  safest choice.
* The single-file form ties the program to its launcher, so killing one
  ends the other. On XP this uses a small helper process instead of a Job
  Object feature XP lacks.

[#platforms-unix]
== Linux, macOS and the rest

32-bit Linux::
Everything must be 32-bit: interpreter, compiler, headers, library and
C modules. `luainstaller` notices a 32-bit userland on a 64-bit kernel.

macOS::
Builds for the Mac's own architecture. Universal binaries, code signing and
notarization aren't done for you.

FreeBSD::
Works with the base compiler. No `-ldl` needed.

Android (Termux)::
Runs inside Termux, using its private prefix and temporary folder. There's
no `/bin/sh` or `/tmp`, and none is needed.

[#platforms-native]
== Native C modules

A C module is copied exactly as `package.cpath` finds it. `luainstaller`
doesn't rebuild it, and doesn't copy the system libraries it links to.

So a bundle that uses `luasocket` or `lsqlite3` runs anywhere those modules'
own libraries are present. If the target machine lacks them, ship them
alongside or link the module statically.

[#platforms-matrix]
== How it's tested

The tables above describe what the code supports; the list below is what
gets tested. It's evidence, not a platform allowlist: a system that isn't
listed may still work.

[cols="2,1,3",options="header"]
|===
|System |CPU |Tested

|Linux |x86_64 |every change, all five Lua versions
|Linux |x86 |every change
|Windows (MSVC) |x86_64 |every change, all five Lua versions
|Windows XP API |x86, x86_64 |every change, by compiling and inspecting the executables
|Linux |ARM64 |on real hardware, before releases
|macOS |ARM64 |on real hardware, before releases
|FreeBSD |x86_64 |on real hardware, occasionally
|Android (Termux) |ARM64 |on a real phone, occasionally
|===

[#platforms-limits]
== Out of scope

* Cross-compiling, or one executable for several systems
* Collecting every system library a C module needs
* Bytecode-only builds, encryption or obfuscation
* Signing the executable, or checking it hasn't been tampered with
* macOS universal binaries, signing and notarization
* Installer packages such as MSI, PKG, DEB or RPM

The single file is just an executable that unpacks itself. It isn't an
installer.
