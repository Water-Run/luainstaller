（已发布的 `v1.5.0`）。这是本轮审计记录，不是用户使用指南。

== 结论

基线 1.5.0 存在本报告记录的生产阻断问题。1.5.1–1.5.3 已发布对应整改，
1.5.3 的精确提交完成必需原生门禁、完整本地回归、公开资产身份与实际默认安装验收。
当前可在可信工具链、受控工作区和有资源配额的构建 worker 中按已声明的平台边界使用。
这不构成任意代码沙箱、零停机目录切换、断电持久性或所有物理平台的验收保证。
1.6.0 的新能力仍需独立回归与发布门禁，不沿用 1.5.3 的通过结果。

本次没有把默认运行用户代码、未实现代码沙箱、未自动收集系统依赖等已声明边界
直接算成漏洞；也没有把静态推断写成所有系统都已复现。审计无法证明不存在其他缺陷。

基线包含 171 个受版本控制的文件，其中 Lua 文件 112 个、C 文件 6 个，
还含生成内容的嵌入副本。未读取或纳入用户未提交的聊天导出，未修改原有 1.5.0 计划。
本次不把未知来源程序作为可信构建输入，不对生产系统实施渗透测试。

威胁模型包括：攻击者可放置工作目录文件；项目或原生模块输入异常；构建进程被杀；
多个程序共享同一单文件缓存；磁盘和工具不可用；维护脚本参数误配。
同 UID 的任意代码执行、编译器被控制及管理员接管整个机器，属于另一个信任边界，
不能靠包内 SHA-256 或字符串转义解决。

== 已验证的优先问题

[cols="1,1,4,2",options="header"]
|===
|编号 |优先级 |问题 |证据
|A01 |P1 |工作目录中的同名 Lua 文件可抢先替代已经打包的 C 模块 |onedir、onefile 均复现
|A02 |P1 |目录替换中断会使正式输出路径消失，恢复流程未恢复旧备份 |发布边界 SIGKILL 复现
|A03 |P1 |单文件解包失败会删除此前匹配成功的共享缓存文件 |实际生成程序复现
|A04 |P1 |部分操作无执行时限；缺少 GNU timeout 时请求的超时被静默忽略 |有/无 timeout 对照及 runtime 扫描
|A05 |P2 |目录名中的 `;`、`?` 破坏 native 模块加载 |完整 bundle 重定位复现
|A06 |P2，有前提 |重链接辅助工具直接执行 payload manifest |无害 marker 写入复现
|===

P1 表示本轮生产就绪目标的优先阻断项，既包含安全影响也包含可用性影响；
并不表示每项都是无需条件的远程代码执行漏洞。

=== A01：已打包的 C 模块可被宿主 Lua 源码覆盖

位置：`src/cgen.lua` 的 `configureNativePath`、`install`；
`src/bundler.lua` 生成启动器时仅传入 Lua 模块映射。

内嵌 Lua 搜索器排在普通 Lua 搜索器之前，但 bundled C 模块仍走后面的 C 搜索器。
当工作目录含有 `auditnative.lua` 时，`require("auditnative")` 会执行该文件，
即使 `.luai/native/auditnative.so` 已正确打包。无需修改程序或设置恶意环境变量。

复现结果：同一个 onedir / onefile 程序在干净目录输出 `native-ok`，
在包含同名文件的目录输出 `shadowed-from-cwd`。这与
`docs/USAGE.adoc` 中“包内模块始终优先”的承诺不一致。

影响：从不可信目录启动工具、处理外部项目的服务，可能执行攻击者放置的模块，
权限等于应用进程。它也会造成难以诊断的环境相关行为差异。

整改：把 bundled C 模块纳入明确的加载映射，在宿主 Lua 搜索器之前按包内实际文件加载。
包内已声明模块加载失败时返回原错误，不能退回宿主同名模块。覆盖点分名称、C root、
连字符入口符号以及五种 ABI，并同步双语文档契约。

=== A02：发布不是抗崩溃的完整事务

位置：`src/bundler.lua` 的 `commitStagingDirectory` 与 `recoverStaleOutputLock`。

当前发布先把旧目录改名为备份，再把暂存目录移到正式路径。两步之间进程退出，
正式路径就不存在。锁记录包含 staging，但不包含完整的备份和提交阶段，
下一次构建主要回收死锁和暂存目录，无法按事务记录恢复旧产物。

复现：在实际旧目录重命名成功的边界杀死专用构建进程组，退出码为 SIGKILL；
正式目录消失，备份中的旧程序仍能运行。重试构建成功后，旧备份仍遗留。
故障注入只暂停该次重命名后的控制流，没有修改文件系统 API 的实际返回结果。

整改：记录和持久化事务阶段及备份身份，逐个边界测试重启恢复。
同时区分普通进程失败、机器断电持久性和在线零停机切换；不能把两次 rename
宣传成跨平台无间隙原子交换。已有长期运行服务还需明确部署切换策略。

=== A03：失败清理破坏共享缓存

位置：`src/onefile.lua` 生成 C 的 `luai_extract_all` 错误清理循环。

错误清理按已遍历文件数删除所有此前文件，未区分本轮新建文件和以前已存在、
本轮仅验证一致的文件。同一个 payload 缓存可能被其他进程使用。

复现：先正常启动建立缓存，再把后续的 `THIRD_PARTY_NOTICES.md` 改为目录，
令下一次启动正常拒绝该不安全类型。启动返回 1，同时此前存在且匹配的
`.luai/native/auditnative.so` 被删掉，缓存中的内部程序仍然存在。

影响：一个启动失败可能使另一个已经运行、稍后才加载 native 模块的进程失败。
这不是只有攻击才会出现的问题：空间、权限或损坏导致的后续解包失败也经过同一分支。

整改：只清理本轮尚未完成的临时文件，不删除其他运行者可见的已提交缓存内容；
保留逐文件原子写入与逐次内容校验。测试两个活动进程及中途写入失败。

=== A04：超时保障不完整

位置：`src/process.lua` 的 `output` / `outputCommand`；
`src/discovery.lua` 的 interpreter probe 和 `runtimePlan`；
`src/toolchain.lua` 的若干工具探测调用。

`timeout_seconds` 只在发现具有特定 GNU CLI 的 `timeout` 时生效。
未发现时执行原命令，不返回能力不足错误。runtime 扫描根本没有传入执行时限。
编译器 `--version`、某些库检查和 ABI 运行探测也不是全部有界。

复现：相同的 2 秒受控命令，1 秒时限在 GNU timeout 存在时约 1.04 秒返回失败；
PATH 仅含 POSIX shell 时约 2.03 秒后返回成功。设置 `LUAI_CMD_TIMEOUT=1`
的 runtime 分析仍约 2.05 秒后成功；当前该变量实际主要影响编译器相关路径。

影响：服务型程序的 runtime 扫描、异常工具或持有 stdout 管道的后代进程
可以无限占用构建任务。未在真实 macOS/FreeBSD 上重复此新探测，不能将模拟 PATH
等价为那些平台的实测结果。

整改：统一有界进程接口，明确超时、取消、子孙进程及输出大小的契约。
为缺少 GNU timeout 的受支持系统提供经过验证的实现，不能静默降级。
给 runtime 模式可配置时限和清楚的超时错误。

=== A05：合法重定位路径被解释为搜索模板

位置：`src/cgen.lua` 的 `configureNativePath`。

实际目录直接拼接到 `package.cpath`；分号被当作列表分隔符，问号被当作模块名占位符。
把完整 bundle 放进 `relocated;directory` 或 `relocated?directory` 后，
同一程序从成功变成 native 模块找不到。Linux 上这两种目录名都是合法的。

整改：已知 bundled 模块按完整字面路径加载，与 A01 的修复结合；
测试安装路径和移动后的路径，不仅测试构建输出名字。

=== A06：重链接清单是可执行程序

位置：`tools/generate-onefile-payload.lua:310`。

工具先 `loadfile` 并执行 `.luai/build/payload-files.lua`，然后才校验记录和路径。
复现清单只是写入任务目录内的 marker 再返回空表，工具仍执行了该副作用。

前提：用户对攻击者提供或篡改的材料运行该辅助工具。这不等于未启动程序即可远程利用，
也不否认编译、运行第三方项目本来需要信任；问题在于元数据处理不必获得任意 Lua 能力。

整改：使用非执行式数据解析，或迁移为严格限定的清单格式，同时保持已发布材料的可重链接性。
加入拒绝代码、字节码、超深结构和非普通文件的测试。

|P2，静态确认
|POSIX 进程输出使用 `read("*a")`；Windows 输出缓冲持续增长。

|R05
|待真实平台验证
|Windows 桥接使用 UTF-16，但生成启动器和 extractor 仍有 ANSI API 与系统代码页边界。

|R06
|边界要求
|POSIX 构建文件操作大量依赖路径检查后再操作，祖先目录并未普遍以句柄固定。
构建根应由可信用户独占；共享可写祖先和同 UID 对抗不是当前已证明的安全隔离能力。
|R07
|样例部署风险

样例需要失败默认值或明确隔离约束，不能仅警告后继续使用弱配置。

== 现有有效防护

* 文本 Lua 入口拒绝二进制 chunk；静态语法验证不执行项目入口。
* 依赖发现、manifest、生成和拷贝间有 SHA-256 快照检查，能够拒绝源码中途变化。
* 输出所有权标记包含完整文件清单与摘要，避免随意覆盖用户改动的目录。
* onedir 使用私有暂存、锁和检查过的备份删除；onefile 发布使用不覆盖已有目标的操作。
* POSIX 解包采用 openat / O_NOFOLLOW、UID 与目录权限检查；Windows 有 ACL 和 reparse 检查。
* argv 引用与 Windows 原生调用区分，工具链采用实际编译与运行的 ABI 探测。
* 下载的测试来源与 CI actions 大多固定到摘要/提交；两个 CLI 和独立安装都有现有测试。

这些措施仍有价值，整改应保留它们，不能为了新模式取消已有防护。
内容摘要用于一致性和恢复，不等于发布者身份认证或程序签名。

== 验证证据与限制

本轮主机：Linux x86_64，Lua 5.4.8，GCC 16.2.1。20 组现有 suite 退出码均为 0，
包括安装、原生依赖、生成 C、构建中断、生命周期、许可证/重链接、可重现性、
`production_edges`、`smoke_all` 和隔离文件系统中的无 Lua 目标。
`production_edges` 输出 129 个用例通过；另行检查 strict prerequisites 成功。
平台条件分支可能跳过，129 不能当成 129 个跨平台行为全部运行过。

独立新增探测证据：

* A01：干净与污染 CWD，分别运行实际 onedir 和 onefile 产物。
* A02：真实重命名后 SIGKILL，检查正式路径、旧备份可运行及重试后的残留。
* A03：后续缓存条目类型错误，检查先前有效 native 文件的存留。
* A04：GNU timeout 有/无两种路径；runtime 扫描的受控延时输入。
* A05：完整 bundle 移动到包含特殊字符的目录。

== 对免解包与字节码评论的评估

Lua 源码已经内嵌在启动器中。纯 Lua 加上静态 Lua 库可以形成直接运行的单文件，
不必先引入字节码支持。含动态 C 模块或 Lua 动态库的产物，仍有系统加载器需要的文件问题；
仅把源码改为字节码不能消除这部分解包。

1.6.0 按用户要求提供自动、解包、免解包三种模式，能力不足时显式诊断。
MoonScript 在构建期调用本机编译器，产物继续使用普通 Lua 加载流程。

预编译字节码的主要收益是省去加载时编译，不能假定执行更快或文件更小；
其格式依赖版本与机器配置，不能接受任意外部字节码并把它当安全沙箱。
依据：https://www.lua.org/manual/5.1/luac.html[luac 官方说明]、
https://www.lua.org/manual/5.4/manual.html#pdf-load[Lua load 的安全与模式说明]。

=== v1.5.3（已发布）

A04 / R01：原生 POSIX supervisor 和 Windows Job Object 路径使用时限与捕获字节预算。
POSIX 无需 GNU timeout；回归覆盖退出码、参数、超限、取消和属主死亡后的进程组清理。
运行时发现默认 30 秒；单源码 8 MiB、bundle 128 MiB、trace 32 MiB，可通过选项调整。
生成器分块写 C 数组、增量计算 payload 摘要。相同 3 MiB 源码在 Lua 进程 192 MiB
软内存限制下，旧生成器失败、新生成器完成。此对照不是跨平台 RAM 配额保证；
第三方编译器、用户代码与磁盘仍需部署环境的资源限额。
Windows 第一次桥接编译仍依赖可信本机编译器与 OS 启动路径，应由构建 worker 的
总时限约束；文件系统阻塞和主动逃离进程组的代码也不构成包内沙箱保证。

R05 / R06：Windows 保留有效 UTF-8 输出，源码哈希走 Unicode 路径接口，捕获输出有界。
文件操作固定非 reparse 祖先句柄，发布前比对文件系统身份；POSIX 检查祖先所有者、
写入权限、链接和身份。配置的临时根、Windows 工作区 ACL 及同 UID 的代码仍是信任边界。
真实 Windows 回归尚未验收，不能由严格 MinGW 编译推断 MSVC 或所有代码页已验证。

意外异常回归覆盖 runtime 中断和 onefile 生成抛错，并确认本次临时工作区被回收。
R03 的断电持久性和 A02 的路径切换间隙仍保留明确边界，不用 flush/close 宣称 fsync 保证。

R07：样例拒绝非 loopback 监听、空或短令牌、通配 CORS 和未实现的密钥认证配置，
不再使用默认 Firebird 密码。请求体、SQL 长度和结果行数有硬上限；数据库侧仍需设置
语句超时和最小权限，样例没有因此成为生产数据库管理服务。行为回归已在本机通过。

并发日志使用 60 秒锁等待预算、错开退避和时钟回退检查。完整本地 24 组套件
曾通过，但提交 `223a903` 的原生门禁仍在日志并发测试失败，不能据本地结果关闭风险。

== 安装渠道补充审计

已发布包的身份核验不能代替安装渠道验证。本机普通用户与 sudo 读取不同配置；
root 原来仅使用未同步的镜像。在改为官方优先、镜像备选后，实际观察到官方索引
下载中断触发旧镜像回退，LuaRocks 将 1.5.1 自动替换为 1.4.0，日志命令随之消失。
这是已复现的可用性与版本选择风险，属于生产交付的阻断项。

整改采用官方源专用配置及系统 HTTPS 下载器，开启证书校验，保留原配置私有备份。
系统已恢复 1.5.1；三次串行默认安装和官方源不可用的空缓存故障注入均完成验证。
断网测试返回错误并保留 1.5.1，没有旧镜像下载或降级。镜像传播仍由外部服务控制；
发布验收和故障排查文档必须核对实际源，不能承诺任意第三方镜像立即同步。

本机 LuaRocks 3.13.0 默认关闭下载器证书校验，已在 root 配置开启；
这是外部客户端的环境风险，不是 luainstaller 自身实现的 TLS 协议漏洞。
涉及同一安装树的发布后安装和故障注入按顺序执行，避免把并发锁冲突误判为下载故障。
