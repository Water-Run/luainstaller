This guide covers everyday packaging: the workflow, the options, how
dependencies are found, and the Lua API. Examples use the short `luai`
commands; `luainstaller build` and friends do the same thing.

toc::[]

[#usage-workflow]
== The workflow

. Make sure the script runs with plain `lua`.
. Check its dependencies with `luai -a`.
. Build a directory bundle.
. Run the bundle with Lua's search paths cleared.
. Build a single file, if you need one.

Using the example program that ships with the repository:

[source,bash]
----
lua test/runtime_bundle/main.lua Ada                       # <1>
luai -a test/runtime_bundle/main.lua                       # <2>
luai -b test/runtime_bundle/main.lua -o build/demo         # <3>
env -u LUA_PATH -u LUA_CPATH build/demo/demo Ada            # <4>
luai -b --file test/runtime_bundle/main.lua -o build/demo1 # <5>
----
<1> Runs normally and prints `hello Ada`.
<2> Lists the modules that will be packaged.
<3> Builds the folder `build/demo/`.
<4> Runs the bundle without help from your installed Lua modules.
<5> Builds a single executable.

TIP: The executable is named after the output folder. Use `-o build/myapp`
to get `build/myapp/myapp`.

[#usage-onedir]
== Directory bundle or single file

[cols="1h,3,3",options="header"]
|===
| |Directory bundle (`--dir`, default) |Single file (`--file`)

|You get
|a folder with the executable and a hidden `.luai/`
|one executable

|Startup
|runs directly
|unpacks to a temporary folder first, then runs; later starts reuse it

|Good for
|debugging, installers, anything you'll unzip
|handing someone one file
|===

Your script and pure-Lua modules are compiled into the executable. Native C
modules and, on some systems, the Lua library sit in `.luai/native/`.

Modules in the bundle always win over the same name on the host. The bundle
isn't a sandbox, though: a module you forgot to package can still be picked
up from the host if it happens to be installed there. That's why step 4
above clears `LUA_PATH` and `LUA_CPATH`.

To start fresh, delete the output folder. `luainstaller` rebuilds its own
output in place, but it won't overwrite a folder you changed by hand or one
it didn't create.

[#usage-discovery]
== How dependencies are found

There are three modes, chosen with `-d`.

static (default)::
Reads your source and follows literal `require` calls such as
`require("json")` or `pcall(require, "socket")`. It starts from the
entry script's folder, then uses `package.path` and `package.cpath`.
+
A computed name like `require("drivers." .. name)` can't be followed and
stops the build with `DynamicRequireError`. Add those modules with
`--include`, or switch modes.

runtime::
Runs the script once and records what it actually loads. Arguments after
`--` are passed to the script:
+
[source,bash]
----
luai -a app/main.lua -d runtime -- --profile demo input.json
----
+
WARNING: The script really runs. Don't use this mode on code that writes
files, talks to the network or starts services when it loads. Only the
code path taken on this run is recorded.

manual::
Scans nothing. You list every module yourself:
+
[source,bash]
----
luai -b app/main.lua -d manual \
  --include app/core.lua \
  --include app/db/sqlite.lua
----

Paths given to `--include` keep their position relative to the entry
script, so `require("db.sqlite")` still finds `app/db/sqlite.lua`.

[#usage-native]
== Native C modules

C modules are found through `package.cpath`, the same way Lua finds them.
Point the environment at the same folders your program uses:

[source,bash]
----
LUA_PATH='/opt/app/share/lua/5.4/?.lua;;' \
LUA_CPATH='/opt/app/lib/lua/5.4/?.so;;' \
luai -b app/main.lua -o build/app --max-deps 250
----

Afterwards, check what was copied:

[source,bash]
----
ls build/app/.luai/native/
ldd build/app/app        # otool -L on macOS
----

`luainstaller` copies each module file but not the system libraries it may
depend on. If a module needs, say, `libssl`, that library has to be present
on the target machine.

[#usage-options]
== All options

.Output
[horizontal]
`--dir`:: directory bundle (default)
`--file`:: single executable
`-o PATH`:: output path

.Dependencies
[horizontal]
`-d MODE`:: `static` (default), `runtime` or `manual`
`--no-depscan`:: same as `-d manual`
`--include PATH`:: add a `.lua` file the scan missed
`--exclude NAME`:: leave out a dependency (path, file name or path suffix)
`--max-deps N`:: stop if more than N Lua modules are found (default 36)

.Toolchain
[horizontal]
`--lua PATH`:: interpreter used by runtime discovery; must be the same Lua
version as the one running `luainstaller`
`--lua-prefix PATH`:: where to find Lua headers and library, when automatic
detection picks the wrong ones
`--target-os OS`:: fail unless the build machine is this OS; there's no
cross-compiling

.Other
[horizontal]
`--verbose`:: print more detail while working
`-- ARGS`:: arguments passed to the script during runtime discovery

[#usage-logs]
== Logs

Each command writes a short record to `~/.luainstaller/`. Only the long
command name can read them:

[source,bash]
----
luainstaller logs
luainstaller logs --level error --limit 20
----

The terminal output and compiler messages usually say more than the log.

[#usage-api]
== Library API

[source,lua]
----
local luainstaller = require("luainstaller")

local analysis = luainstaller.analyze({
    entry = "app/main.lua",
    max_deps = 120,
})
if not analysis.ok then
    io.stderr:write(analysis.error.type, ": ", analysis.error.message, "\n")
    os.exit(1)
end

local built = luainstaller.bundle({
    entry = "app/main.lua",
    mode = "onefile",          -- or "onedir" (default)
    out = "build/app",
})
print(built.ok and built.executable or built.error.message)
----

[cols="1m,3",options="header"]
|===
|Function |Does

|analyze(opts)     |list dependencies, like `luai -a`
|trace(opts)       |explain how each dependency was resolved, like `luai -t`
|compatibility(opts) |check the toolchain and platform without building
|bundle(opts)      |build, like `luai -b`
|getLogs(opts)     |return log records (a list)
|clearLogs()       |delete the logs; returns `true` on success
|===

The first four return a table with `ok`. When `ok` is `false`, `error.type`
and `error.message` explain why; the types are listed in
xref:TROUBLESHOOTING.adoc#troubleshooting-errors[Troubleshooting].

Option names match the command line with underscores: `max_deps`,
`discovery_mode`, `include`, `exclude`, `lua_prefix`, and so on. An unknown
option is an error rather than being ignored.

The version is `luainstaller.VERSION`.
