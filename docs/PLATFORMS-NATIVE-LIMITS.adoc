[#platforms-contract]
== Native host

The product removes the need for a separate system `lua` command. It does not
translate ABIs, emulate other operating systems, or cross-compile. Build and
run on the target-class environment.

Align: OS family and loader conventions, CPU architecture, system/compiler
ABI, Lua major/minor ABI, and native modules with their system dependencies.

There is no cross-build mode. `--target-os` only asserts the detected host OS;
mismatch → `UnsupportedPlatformError`.

[#platforms-lua]
== Lua

* official Lua `>= 5.1` and `< 5.6`
* LuaJIT is rejected
* analysis interpreter, tracer, headers, linked library, and bundled C modules:
  one major/minor
* launchers are generated for the active ABI; a native linked-runtime probe
  before publish requires `_VERSION` to match the build interpreter

[#platforms-toolchains]
== Toolchains

[cols="1,2,3",options="header"]
|===
|Host |Runtime strategy |Typical requirements

|Linux / Android / BSD / other ELF POSIX
|Verified shared liblua copied into `.luai/native`, or verified static
`liblua.a`
|C99 compiler, matching headers and library; `pkg-config` is optional when an
explicit prefix or LuaRocks metadata is complete

|macOS
|Static `liblua.a` preferred; matching dylib accepted after a native probe
|Apple compiler and matching headers/library

|Windows
|ABI-specific DLL beside the executable and under `.luai/native`
|Native x86/x86_64/ARM/ARM64 compiler, headers, import library and matching DLL
|===

When automatic discovery is insufficient, use `--lua-prefix` or
`LUAI_LUA_PREFIX`. An explicit prefix is authoritative; discovery does not
silently substitute another install. The prefix is for the current host and
ABI, not a cross SDK.

Explicit prefixes are searched in `lib`, `lib64`, `lib32`, common Linux
multiarch subdirectories, and the prefix root.
ABI-versioned shared files and relative links contained by the prefix are
supported; links that escape it are rejected. Compiler/run probes and loader
inspection use the same `LD_LIBRARY_PATH` or `DYLD_LIBRARY_PATH`, so a probe
cannot validate one runtime and record a different system runtime.

A static POSIX launcher is linked with exported main-program symbols so a
normal `luaopen_*` module can resolve the Lua C API. Custom installs may set
`PKG_CONFIG_PATH`. Candidate filtering happens before the compiler probe:
POSIX accepts shared objects and static archives, macOS accepts `liblua.a` and
dylibs, and Windows accepts DLL import libraries (`.lib` or `.dll.a`) paired
with a matching DLL. The compile-and-run probe selects the actual link mode;
the launcher-profile name is not an allowlist. A macOS dylib fallback is
published only when the linked Mach-O records it as `@rpath/<runtime-name>`,
so copying it into `.luai/native` does not retain a path to the build host.

Android/Termux is detected independently from desktop Linux. It uses the
Termux `TERMUX__PREFIX` (with legacy `PREFIX`/`TERMUX_PREFIX` fallbacks), a
shell found through `PATH` (there is normally no `/bin/sh`), Bionic-compatible
native objects, and `TMPDIR` or the prefix's `tmp` directory for onefile
extraction. The Android extractor recognizes system-UID-owned `/data`
ancestors before requiring the app-private part of the path to be owned by the
Termux UID. FreeBSD does not receive Linux's `-ldl`; its launcher
uses `KERN_PROC_PATHNAME` and falls back to resolving `argv[0]` through
`PATH`. `ldd` is useful evidence but is no longer mandatory when the exact
accepted shared library has passed the ABI probe.

On a 32-bit userland, `getconf LONG_BIT` corrects a 64-bit-kernel `uname`
result. The running Lua, compiler default target, headers, libraries and
native modules must all be 32-bit; `-m32` on only one build step is not a
complete toolchain.

MSVC builds use the static multithreaded CRT (`/MT`) for the Lua DLL, launcher,
native capability module, and onefile extractor. Release tests inspect PE
dependencies and reject `VCRUNTIME*.dll`, `MSVCP*.dll`, or `ucrtbase.dll`, then
run the artifact in a clean Windows VM without a VC Redistributable.

Windows x86/x86_64 generated C defaults to `_WIN32_WINNT=0x0501`; executable
links also record subsystem 5.01 for x86 or 5.02 for x86_64. Windows XP can
therefore run an artifact only when the selected compiler/CRT and the Lua DLL
were also built for XP. Onefile tries Job Object kill-on-close containment;
when XP rejects that newer limit flag, the outer executable starts a small
copy of itself as an inherited-handle watchdog. The watchdog waits on the
outer process and terminates the same job after an abrupt exit; normal exit
terminates the job explicitly. For building on XP, use PowerShell 2 or newer,
start from the compiler's prepared command prompt, set `LUAI_CC` when compiler
discovery tools are absent, and normally pass an explicit `--lua-prefix`.
Modern MSVC/UCRT output is not made XP-compatible merely by the preprocessor
value; use an XP-capable MSVC toolset or MinGW runtime. ARM/ARM64 uses the
Windows 6.2 API baseline because Windows on ARM did not exist on XP.

macOS does not produce universal binaries, code-sign, or notarize. Windows
builds and probes run natively; Wine/MinGW are not part of the release path.
Generated runtime code uses Win32 `A` path/process APIs for the XP floor.
Non-ASCII paths therefore remain limited by the active Windows code page;
ASCII distribution paths are the portable choice for XP.

[#platforms-native]
== Native Lua C modules

Discovery copies the file selected from `package.cpath`. It does not rebuild
for another OS/arch/ABI, rewrite RPATH, recursively package system libraries,
or audit licenses.

[source,bash]
----
LUA_PATH='/srv/app/share/lua/5.x/?.lua;;' \
LUA_CPATH='/srv/app/lib/lua/5.x/?.so;;' \
luai -t app/main.lua --max-deps 250
----

Toolchain acceptance compiles an ordinary `luaopen_*` C module, deliberately
without linking liblua on Linux, and loads it through the same host/runtime
profile. This proves Lua-symbol visibility for normal modules. It does not
prove closure of every application module's additional system dependencies.

[#platforms-limits]
== Out of scope

* cross-compilation / one binary for many platforms
* automatic closure of all native system libraries
* bytecode-only packaging, encryption, obfuscation
* signing, tamper-proofing, or authenticity verification of the produced
  executable (the onefile payload ID is a cache key only)
* loading native modules from single-file without extraction
* macOS universal / signing / notarization
* MSI / PKG / DEB / RPM generation

Single-file is an executable distribution form (extract then start), not an OS
installer.
